# docs/07 — 资金费率套利策略集成方案（Funding Rate Strategy Integration）

> v1.0 | 2026-09-20 | VeriAgent × Funding Rate Arbitrage
> 前置：docs/01-04 四件套；本方案为策略层扩展设计，凭证先于交易原则不变
> 状态：设计文档（Phase 0）——待用户审阅后进 Phase 1 编码

## 1. 目标与定位

将资金费率套利（funding rate arbitrage）作为 **VeriAgent 策略层的新决策源**接入：
策略输出仍走完整凭证链路 `Decision → record() 上链 → bindTx() → verifyTrade()`，
套利决策与其他交易决策享受同等的不可抵赖审计保证。

**一句话**：Agent 说"我要做费率套利"的那一刻，理由、费率证据、双腿配置已经在链上锚定——
事后无法声称"当时费率不是这样的"。

## 2. 策略模型回顾（操作方法 → 决策对象映射）

| 玩法 | 腿配置 | 决策语义 |
|------|--------|----------|
| 正向套利（吃正费率） | 现货买入 + 永续做空（等名义） | open_arb / close_arb |
| 负费率反向套 | 永续做多 + 借币卖出现货 | open_arb_short_side |
| 跨所费率差/价差 | A 所空腿 + B 所多腿 | open_arb_cross_venue |

核心特征：**delta 中性双腿结构**——收益来自费率现金流，不来自方向判断。

## 3. 决策对象扩展（models.py，向后兼容）

### 3.1 扩展字段（进入 action_payload → 自动被 actionHash 覆盖）

```python
# Decision.action_payload 新增字段（funding 策略决策时填充）
{
  "strategy": "funding_arb",              # 策略血统标识
  "legs": [                                # 双腿配置（canonical 排序后哈希）
    {"venue": "binance", "instrument": "spot",  "asset": "BTC", "side": "buy",  "amount": 100000000, "hedge_role": "spot"},
    {"venue": "binance", "instrument": "perp",  "asset": "BTC", "side": "sell", "amount": 100000000, "hedge_role": "perp"}
  ],
  "funding_snapshot": {                    # 入场时刻费率证据（→ dataSourceHash 强化）
    "venue": "binance", "asset": "BTCUSDT",
    "funding_rate_bps": 3.2,               # 每 8h 费率（bps）
    "next_settle_ts": 1758374400,
    "mark_price": 63250.5, "index_price": 63248.2,
    "open_interest_usd": 4200000000
  },
  "expected_income_bps": 128,              # 预期净收益（扣费后，持仓 4 周期）
  "hedge_ratio": 1.00,                      # 名义对冲比（0.95-1.05 容差）
  "period_hours": 8                          # 结算周期（Binance/OKX/Bybit 标准）
}
```

### 3.2 合约侧零改动（架构优势）

`DecisionRecorder.record()` 链上只存五个哈希——action_payload 结构是**链下约定**，
新增字段自动进入 `actionHash = keccak(canonical JSON)`，链上合约无感知、无需升级。
现有 abi_encode.py ↔ Solidity `abi.encode` 逐字节一致断言继续成立（payload 是变量，机制不变）。

### 3.3 reason 格式（reasonHash 锚定）

```
"funding_arb binance:BTCUSDT rate=3.2bps/8h settle=2026-09-20T16:00Z
 expected_net=128bps(4p) fees=32bps legs=spot_buy+perp_short ratio=1.00
 session=OPEN"
```

### 3.4 model_id 血统

| 策略版本 | model_id | 说明 |
|----------|----------|------|
| 规则版 | `funding-arb-v1` | 阈值规则策略（Phase 1） |
| Jev 接入 | `jev-funding-v1` | TypeSafe System One 参与 funding 决策（远期） |

双轨审计原则延伸：**同一套凭证流水线可审计不同血统的费率决策模型**。

## 4. 感知层扩展（perception.py）

```python
@dataclass(frozen=True)
class FundingRateSnapshot:
    venue: str
    asset: str                 # "BTCUSDT"
    funding_rate_bps: float    # 当前预测费率（每周期 bps）
    funding_rate_avg_8h: float # 近 7 天均值（防单点峰值误导）
    next_settle_ts: int
    mark_price: float
    index_price: float
    open_interest_usd: float
    volume_24h_usd: float
    ts: int
```

- `PerceptionSnapshot` 扩展可选字段 `funding: FundingRateSnapshot | None = None`（向后兼容）
- `context_hash` 覆盖费率快照 → `dataSourceHash` 上链锚定费率证据
- 数据源（Phase 2）：Binance `GET /fapi/v1/premiumIndex`、OKX `GET /api/v5/public/funding-rate`、
  Bybit `GET /v5/market/tickers` —— 全部公开 REST 端点，无需 API key 读费率
- **费率数据源时延声明**：凭证锚定的是快照预测费率，实际结算费率可能不同——
  持仓期每个结算周期的**实收费率**写入本地审计链（JSONL），收益可事后对账

## 5. 策略模块设计（engine/funding_arb.py 新文件）

```python
@dataclass
class FundingArbConfig:
    min_funding_rate_bps: float = 3.0      # 单周期费率低于此不入场
    min_avg_rate_bps: float = 1.5          # 7 日均值门槛（防单点峰值）
    min_notional_usd: float = 500.0
    max_notional_usd: float = 50_000.0
    hedge_ratio_min: float = 0.95
    hedge_ratio_max: float = 1.05
    min_venue_oi_usd: float = 50_000_000.0 # 持仓需深度
    fee_rate_bps: float = 8.0              # 双边建平仓费预算（taker）
    slippage_budget_bps: float = 10.0
    min_expected_net_bps: float = 30.0     # 净收益门槛（4 周期累计）
    periods_to_hold: int = 4               # 计划持仓周期数
    max_funding_notional_usd: float = 50_000.0  # 单决策名义上限

class FundingArbPolicy:
    """参照 DecisionPolicy 模式：费率快照 → Decision or DecisionReject."""

    def decide(self, agent_id: int, snap: PerceptionSnapshot,
               amount_usd: float) -> Decision:
        # 1. session gate 继承（tokenized-equity perp 相关时 HALTED 仍硬拒）
        # 2. 费率门槛：rate >= min_funding_rate_bps 且 avg >= min_avg_rate_bps
        # 3. 流动性：venue OI >= min_venue_oi_usd
        # 4. 净收益测算：
        #    gross = funding_rate_bps × periods_to_hold
        #    cost  = fee_rate_bps (建+平双腿) + slippage_budget_bps
        #    net   = gross - cost; net < min_expected_net_bps → reject
        #    reject 码: "FUNDING_EDGE_TOO_THIN"
        # 5. 对冲比校验：amount_spot/amount_perp ∈ [hedge_ratio_min, hedge_ratio_max]
        #    reject 码: "HEDGE_RATIO_OUT_OF_BOUNDS"
        # 6. 名义上限：reject 码: "FUNDING_NOTIONAL_EXCEEDED"
        ...
```

**决策拒绝码一览**（reasonHash 可审计）：
`MARKET_HALTED / FUNDING_EDGE_TOO_THIN / HEDGE_RATIO_OUT_OF_BOUNDS / FUNDING_NOTIONAL_EXCEEDED / INSUFFICIENT_VENUE_DEPTH / FUNDING_RATE_TOO_THIN`

## 6. 链上 Policy 语义分析（VeriAgentVault.sol 6 规则）

| 现有规则 | 对 funding 套利的语义 | 处理 |
|----------|----------------------|------|
| 白名单 | venue 白名单需含 CEX 名（若链下执行，仅引擎侧消费） | Phase 1 引擎侧 enforce；链下执行模式文档化 |
| 仓位上限 | 双腿名义是否都计敞口？**保守语义：spot+perp 名义都计入 position cap** | 文档化+测试断言 |
| 日亏损熔断 | 套利腿亏损（滑点/费率反转）计入日亏损 | 沿用 |
| 冷却期/频率限制 | 双腿同凭证算一次决策，避免双腿各计一次频率 | 文档化：一决策=一凭证 |
| 暂停 | 引擎执行层消费 pause 信号（链下 CEX 活动无法链上强制平仓） | 诚实标注（见 §10） |

**P1 阶段可选合约扩展**（不阻塞引擎侧集成）：
- `funding_leg_pair_required`：funding 决策凭证必须含 ≥2 legs（单腿 funding 决策拒绝上链）
- `max_funding_notional`：套利决策独立名义上限
- `hedge_ratio_bounds`：链上校验 hedge_ratio ∈ [9500, 10500] bps

**执行模式定位**：CEX 资金费率套利是链下活动——凭证链路价值在于**决策与费率证据的链上锚定**，
`bindTx()` 扩展语义：绑定任意执行证明哈希（CEX 成交回报 fill report 哈希化后提交），
`verifyTrade(decisionHash, executionProofHash)` 语义不变：验证顺序+完整性。

## 7. 审计链增强（recorder.py JSONL）

funding 决策在本地审计链的完整生命周期记录：

```
决策时刻:  decision (四哈希+双腿+费率快照)
执行时刻:  leg_fill_reports (两腿成交回报哈希+实际成交价+滑点)
持仓期:    funding_settlements [{period_ts, rate_bps, income_usd, proof}]  ← 每周期实收入链
平仓时刻:  close_decision + close_fills + realized_pnl_summary
```

链式哈希保证：篡改任何一期结算记录 → JSONL 链断裂 → 验证失败。
**收益验证闭环**：外部审计方可对账"声称的费率收益"与"链上锚定的费率快照+交易所公开结算数据"。

## 8. 测试计划（pytest + forge 双端）

**pytest（Phase 1 引擎侧）**：
- 决策对象扩展哈希稳定性：现有四哈希测试向量**零破坏**（向后兼容断言）
- funding payload canonical 哈希确定性（字段顺序无关）
- 阈值拒绝全矩阵：6 个 reject 码各一条用例
- 净收益测算数值断言（已知费率/费用入参 → 期望 net bps）
- HALTED 门控继承：tokenized-equity funding 决策停牌时段拒绝
- 审计链 funding 生命周期：决策→执行→多周期结算→平仓 JSONL 链完整+篡改检测

**forge（机制兼容性）**：
- DecisionRecorder 对 funding payload 哈希的兼容（payload 新结构 → actionHash 锚定正常）
- HashParity 扩展：funding payload 的 abi_encode.py ↔ abi.encode 逐字节断言
- 若 P1 做合约扩展：leg_pair/hedge_ratio bounds 规则单测

## 10. 风险与诚实差距

| 风险/差距 | 说明 | 缓解 |
|-----------|------|------|
| CEX 托管风险 | 凭证审计不消除资金在交易所的对手方风险 | 单所敞口上限；审计链记录场所分布 |
| 费率数据时延 | 凭证锚定快照预测费率 ≠ 实际结算费率 | §7 结算记录入审计链，收益可对账 |
| CEX 执行真实性 | bindTx 绑定的执行证明依赖交易所 API 回执签名 | fill report 哈希+API 签名验证；信任假设文档化（本表即声明） |
| 链上强制力有限 | 链下 CEX 套利无法被链上 policy 强制平仓（pause/熔断只是信号） | 引擎侧消费信号；定位为"决策审计"而非"执行托管" |
| 单腿风险 | 一腿未成/延迟成交 → delta 敞口暴露 | 决策凭证记录双腿配置；执行期监控 hedge drift（审计链记录 drift_bps）；超阈值告警 |
| 手续费侵蚀 | taker 双边费+滑点可能吃掉薄费率收益 | 净收益门槛 30bps 入场过滤；maker 挂单优先（config 可调） |
| 策略容量 | 高费率时段套利者涌入→费率快速归零 | 7 日均值门槛+费率趋势字段入凭证（事后可审计入场时机合理性） |

## 11. 与现有系统的边界

- **不改变**：四哈希凭证机制/DecisionRecorder/AgentIdentityRegistry/verifyTrade 语义
- **扩展**：Decision.action_payload 字段约定/perception 数据类/strategy 新策略类/审计链记录类型
- **可选**：VeriAgentVault policy 规则（Phase 3）
- **明确不做**：高频做市/方向性杠杆策略——VeriAgent 叙事是"可验证的决策审计层"，不是策略工厂；
  策略源可插拔（Jev/NanoJev/规则版 funding），凭证流水线不变
